# G0: the compatibility gate

G0 records what an electromagnetic (EM) design observes of axionMultiPhysics, and compares every later build with the
record. Its purpose is to make "an existing design behaves as before" a checked statement, so that code which EM
documents execute can be edited (for example to add other physics) without changing their messages, exit statuses,
meshes or numbers. The script is `tests/g0/g0.py`; its pytest wrapper is `tests/test_g0.py`. The data is under
`tests/g0/`.

**Where it runs.** Tier B says "byte-identical", so it needs one pinned platform, and that platform is where the
development gate runs: the MPI build on one node type of the development cluster (platform key
`lawrencium-x86_64-mpi`), in a batch job, with the site toolchain (gcc 13.2, OpenMPI 4.1.6, OpenBLAS 0.3.24) and the
shared MPI third-party stack, one thread, one rank, the mesher's canonical curved-mesh process. Every merge runs tiers
A and B there, against that platform's own record.

The development gate also has a sequential job (the site compiler, the sequential third-party stack and gmsh from
PyPI). Its build is a platform with a name of its own, `lawrencium-x86_64-sequential`, compared at **tier A only**,
against a text record that is made on the cluster. It needs the name because its bare key is a hosted platform's
(`linux-x86_64-sequential`), whose record the cluster cannot make: under that key a declared change of a text could
not pass the gate. No solve is recorded or compared there. That job does not run on the pinned node type and its
mesher is a packaged gmsh, so its bytes pin nothing; its numbers are checked by the physics checks of the test suite,
which the same job runs.

The three platforms of the GitHub-hosted runners (`linux-x86_64-mpi`, `linux-x86_64-sequential`,
`macos-arm64-sequential`) are exercised by `.github/workflows/g0.yml`, which is the public repository's CI at a
release (it is triggered by the release tag `v*`, and by a pull request there) and the only place macOS is covered.
They are compared at **tier A** (against their own committed text record)
and **tier C** (their numbers against the reference platform's record, to the tolerances measured on them), never at
tier B: a hosted runner image moves, so a record of its bytes would be refused more often than it would hold. Their
committed records are the ones their CI runs made, and a manifest entry they have no measurement of is reported as
PENDING, by name and with its reason (below), not passed over.

## What is compared

| tier | what | where | how |
|---|---|---|---|
| A, text | for every design under `examples/`, `benchmarks/designs/` and `tests/g0/designs/` and every template at its defaults: stdout and exit status of `axmp validate`, `axmp resolve` and `axmp template`, and the mesher's input file (the file `axmp mesh` hands the mesher; a stub mesher that exits at once makes `axmp mesh` leave it behind without meshing). For the corpus of invalid documents (`tests/g0/corpus.json`): the stdout and exit status of `axmp validate`, and the type, `str` and `args` of the exception that the binding `axionmultiphysics._core.validate` raises for the document's text (the `Design` class's own file reading is not in the record) | every recorded platform: the reference platform, the sequential build of the development gate, and the three hosted-runner platforms (Linux MPI, Linux sequential, macOS arm64) | equal to that platform's baseline |
| B, bytes | for the solves and meshes of `tier_b` in `tests/g0/manifest.json`: the mesh files, `results.json`, `scene.json`, `axmp_status.json`, the mesher's input and info files, the names of all files in the run directory, the exit status and stdout | the **reference platform** (`lawrencium-x86_64-mpi`: the MPI build on one pinned node type with the site toolchain, one thread, one rank, the mesher's canonical curved-mesh process), against **its own record**, while its fingerprint is the recorded one. That record is also what tier C compares the other platforms with. A host of its own, with a name of its own, is likewise compared with its own record | byte-identical outside the mask list: every file is compared by the hash of its text; in a JSON file the masked values are blanked in place first, so the whitespace, the spelling of every other number and the order of the keys are compared too |
| C, physics | the solves of the same list | every platform but the reference, against the reference platform's record | **what is not a number, exactly**: every boolean (the verdicts of the physics checks: `valid`, `holds`, `pass`, ...), string and null of `results.json`, and its layout (the keys in file order and every list length), equal to the reference platform's, outside the leaves that were measured to differ on that platform and are listed, with both values, in `tests/g0/tolerances.json` (`unasserted_discrete`, `unasserted_layout`). **The numbers, to a tolerance**: the scalar figures of `results.json` against the reference platform's, to a relative tolerance per quantity that is measured from the spread between platforms (below). Each figure is compared relative to the reference value of that figure alone (a value that is zero on the reference must be zero), so a large number elsewhere in the file, such as the 1e30 that stands for "no margin", loosens nothing. No mesh-dependent byte or count is asserted: sizes of the mesh and of its linear systems (`dofs`, `elements`, `nodes`, `nonzeros_*`, `cells`, `faces`, `samples`, ...) are left out by name. The physics checks of the test suite run on every platform as before |

### The fingerprint, and when tier B is refused

The fingerprint (`baseline/<platform>/fingerprint.json`) has two parts. The **compared** fields are the operating
system and C library, the machine, the build kind, the compiler, the **processor model**, the gmsh version of the
mesher, the hash of the dependency pins (`third_party/SHA256SUMS.txt`), the rank count (read from the launcher) and
whether STRUMPACK is linked. The compiler is the ident string in the built library, or, for a binary format without
one, the compiler the build system recorded; `record` never writes a reference fingerprint without it. The thread
count is not a compared field, because it cannot differ: the harness gives every run one thread (`OMP_NUM_THREADS=1`
and the BLAS equivalents). The **informational** fields are the BLAS and LAPACK libraries that the engine, `axmp` and
the mesher load (the file each name resolves to, the distribution package and its version, and for an OpenBLAS its
configuration string and the kernel in use), the environment the harness forces and clears, the runner image, the
Python version and the build information of the package.

**The processor is part of the pin.** The reference platform is one node type, not a cluster. The processor decides
which kernels an OpenBLAS built for several of them picks (below), and nothing else in the record would notice a
node of another model, so `cpu` is a compared field: `g0.py record` refuses on another processor **even with
`--repin`** (`REFERENCE_CPU` in `tests/g0/g0.py` holds the pinned model; changing it is a code change that argues the
new pin and re-records), and `g0.py check` refuses tier B there. The batch job that runs the gate asks the scheduler
for the pinned node type by its feature **and** checks the processor model itself before it compares anything: the
partition of the pinned nodes also holds a group of another model, and a scheduler feature is a label on a node, not
the processor in it.

**What the fingerprint does not pin.** `dependency_pins` is the hash of the dependency versions of the source tree
(`third_party/SHA256SUMS.txt`), not the identity of the installed third-party prefix that the build links. Lines that
name a particle-transport pin (Geant4, Pythia, HepMC3, Xerces-C) are left out of the hash (`TRANSPORT_PINS` in
`g0.py`): no build that G0 compares links them, so adding one leaves the recorded fingerprints valid. A stack
that is rebuilt or replaced at the same pinned versions can therefore move the compared bytes while every compared
field still matches; the diagnosis `check` prints when nothing differs says so, so that it is not read as a change in
the code. On the reference platform the prefix is the shared stack of the development cluster, which changes only
deliberately; a build against another prefix is a platform of its own and is given a name of its own (below).

A platform is compared with its own record only while its compared fields are the recorded ones. Otherwise tier B is
**refused**: `g0.py check` says so, with the fields that differ, and runs tier C alone. The one exception is the host
that says it is the reference platform: `g0.py check --require-reference` (the gate's own job passes it) turns a
refusal into a failure, because on the pinned node type it means that the processor, the system, the compiler or the
mesher moved, and that needs a separate, argued re-recording, not a gate that quietly drops its byte-level tier. The
flag decides the **role** and is therefore read before the platform key: a host that passes it is compared as the
reference platform whatever key it presents under, including the hosted key `linux-x86_64-mpi` that a cluster node
has unless it is named (below). Otherwise the fingerprint that the flag exists to fail on — one that moved — would
send the host back to its key, where tier B is no part of the gate at all.
A tier-B record written by an older harness, which compared other things, counts as no record (the file carries its
format).

**What a run without tier B leaves unchecked.** A refusal is not a failure, and it is not the same pass either.
`check` then prints one line, `G0 ran WITHOUT TIER B on <platform>: ...`, with the reason and the number of figures
that tier C compared with nothing, and its last line is `G0: passed WITHOUT TIER B` (the exit status stays 0; a
difference that tier C does see still fails). Nothing checks, in such a run:

- the figures of `results.json` that `tests/g0/tolerances.json` lists as `unasserted` for the platform (for its own
  family if it was measured, for `any` otherwise), the mesh-sized quantities, and the figures no spread was measured
  for there: these are the ones the line counts. The figures of an entry that is pending on the platform are not
  compared either; `check` names those entries;
- a change of any figure below its tolerance, and the arrays of more than 64 numbers, of which tier C compares the
  length only;
- every other file of a run: the mesh files, `scene.json`, the status file, the mesher's input and info files, the
  names of the files, and stdout. Tier C reads `results.json` and the exit status.

Whenever tier B or tier C fails, `check` prints how the host differs from the fingerprint recorded for its platform,
informational fields included, so that a platform that moved (another processor, another build of the BLAS package)
can be told from a change in the code.

**The BLAS kernel.** An OpenBLAS built for several processors picks its kernels from the processor it starts on, and
they round differently. A hosted CI image runs on more than one processor model, and that showed: two records of the
same sources on the then-reference hosted image (workflow runs 44073582042 and 44081826913) differed in 50 leaves of
one `results.json`, all under `/electrostatics` of `example_pickup_capacitance`, in the last digits (1e-14 relative on
the capacitances). On a cluster node, the same 50 leaves and no others change when OpenBLAS is told to use its
SkylakeX kernel instead of its Haswell or Zen kernel. The harness therefore gives every x86_64 run
`OPENBLAS_CORETYPE=HASWELL`, a kernel every such processor has. This is belt and braces beside the pinned processor
model: the kernel is pinned even where the processor is not, which is every platform but the reference. A fingerprint
written by the present harness says so in its informational part (`environment_forced`, and the kernel the library
reports under `blas`).

**Address-space randomisation.** A mesh must not depend on where the mesher's memory happens to lie. On Linux the
mesher sees to that itself: `axmp-mesher` starts itself again with address-space randomisation switched off (unless
`AXMP_MESHER_ASLR=on` is set) and reports what it ran with as `address_randomization` in the info file of a 3D mesh
(`"off"`, `"on"`, or `"unknown"` where the operating system has no such switch, as on macOS). G0 relies on that and
checks it: the harness removes `AXMP_MESHER_ASLR` from the environment of every run; the info file is one of the
files tier B compares, so a mesher that stopped switching randomisation off changes a compared byte; and `record`
gives no record to an entry whose mesh was made with randomisation on. Beside this, every entry is run twice by
`record`, in two processes and two output paths, and again by every later `check`, so a mesh or a number that
depended on addresses in spite of it would show as a difference.

### Which solver each platform links, and the gap

The reference platform links **STRUMPACK** (the shared MPI third-party stack has it), so the pinned bytes are those of
the STRUMPACK build. `g0.yml` builds MFEM, hypre and METIS from `scripts/build_deps.sh` (MPI) and
`scripts/build_deps_wheel.sh` (sequential); neither builds STRUMPACK, so **all three hosted platforms use the Eigen
sparse-LU fallback**. Which sparse LU is linked is a compared fingerprint field, and the difference between the two is
part of the platform-to-platform spread that sets the tier-C tolerances: it is measured, not assumed away. What no
platform holds is a byte record of the **Eigen** build; a host that wants one gives itself a name of its own (below)
and records under it.

The two platforms that take gmsh from PyPI (Linux sequential and macOS) install the release the reference platform's
mesher is built from (`gmsh==4.15.2` in `g0.yml`), not a range: another release gives other meshes, and their
tolerances and records were measured with this one.

### The tier-B list

`tier_b` in the manifest lists the solves that finish within the pre-merge budget on one thread (`check` runs the
whole list, tier A included, in a little over three minutes on one core of a cluster node; the longest entry is
`solve_3d_ring_curved`, about one minute):

- the three templates, and `examples/cavity_pillbox.json`, `pickup_capacitance.json`, `long_solenoid_coax.json` and
  `hts_shield.json`;
- three small axisymmetric designs of the gate's own (`tests/g0/designs/`), which exist so that every design section,
  shape kind and material block that the examples do not use is parsed by a valid document and reaches a solver:
  `mechanics_axi.json` (a `mechanics` section with supports, a pressure and a cooldown; `mechanical` material blocks;
  a `polygon`), `thermal_axi.json` (a `thermal` section with a fixed temperature and both kinds of load; `thermal`
  material blocks with a constant and a tabulated conductivity) and `circuits_curves_scan.json` (`circuits`, a
  persistent and a powered one; `curves` with segment, arc and polyline paths; a `polygon` with per-vertex fillets
  and a `contour`; materials with `rf` blocks of three models; `scan` and `benchmarks`);
- two solves by the 3D engine (MPI builds only): `ring3d.json`, a winding ring and a slit superconducting pickup
  ring at element order 1, and `ring3d_curved.json`, the same at order 2 on a curved mesh made in the mesher's
  canonical process;
- two meshes without a solve (`axmp mesh`): `benchmarks/designs/stage1_twoport.json` and the same design with
  `mesh.order` 2.

The 3D solves of the examples (`comsol_toroid_*`) and the benchmarks `curved_probe_shell` and `solenoid_exterior`
take several minutes to hours and are not in the list; their `validate`, `resolve` and mesher input are in tier A.
`tests/test_g0.py` keeps the list from losing its 3D solves, its mechanics and thermal solves and its coverage of the
sections, shape kinds and material blocks.

### Paths, the mask lists, and entries without a record

Output directories differ between runs, so every occurrence of the run's own directory in text is replaced by `<OUT>`
before comparing, and the checkout's directory by `<ROOT>`. Anything else that varies is found by measurement:

- **Reproducibility measurement.** `g0.py record` runs tier A twice and every tier-B entry twice, on every platform;
  the second time in an output directory with a different path length (mesh identity has depended on the path
  length). On the reference platform the record is also checked again on **other nodes of the pinned type**, which is
  what tells a difference between two runs from a difference between two machines of the same model. A text stream of
  tier A that differs goes on the platform's mask list
  (`baseline/<platform>/masks.json`) with the difference as its reason. A JSON leaf of tier B that differs and is a
  **timing or run identity by its name** goes on the list with that reason.
- **What a mask may name.** A leaf is a timing or run identity by its whole name, never by a substring: `seconds`,
  `*_seconds`, `hostname`, `pid`, `timestamp`; `*_s` directly under a `timing` object; and the three per-solve
  timings that the 3D solver logs, `clean_s`, `setup_s` and `solve_s`, in an item of `/solver/solves`.
  `newton_update` contains "date" and `q_wall` contains "wall", and both are physics; so are `iterations` and
  `relative_residual` in the same solver log.
- **An entry that is not reproducible has no record on that platform.** If anything else differs between the two
  runs (a leaf of any other name, a mesh file, the set of files, the stdout or the exit status), or if the mesher
  reports that a curved mesh was not made in its canonical process or that address-space randomisation was on, the
  entry gets no tier-B record there. It is listed **by name** in `masks.json` (`tier_c_by_name`) with what differed,
  and `record` prints `NO RECORD of <entry>` for it. Its figures are no record either, because one of two values that
  disagree is not a reference:
    - **On the reference platform nothing of the entry is written**, also not to `figures.json`, so no platform is
      compared with it, and nothing compares it there, because tier C does not run on the reference platform. Such an
      entry is pending on the reference platform (`tests/g0/pending.json`) and `check` fails for it, naming the entry
      and what differed. It is made reproducible or taken off the manifest; it is not left in as an entry the gate
      passes over.
    - **On any other platform both runs are kept** in its spread file (the second under `second_run`; the timings
      are dropped from both). Tier C compares the entry with the reference platform's record, and its tolerances are
      derived from the larger of the two spreads: a tolerance from one run alone could be one that the platform's own
      second run fails.

  No physics leaf is ever masked.
- The mask lists are per platform, reviewed, and may only shrink. `g0.py record` enforces it: a mask or a by-name
  entry that the committed list for the platform does not have makes `record` stop (exit status 3) and print it,
  unless `--allow-new-masks` is given for a first baseline, for a new manifest entry or for a reviewed addition.
  `tests/test_g0.py` checks that every tier-B mask names a timing or run-identity leaf and that no tier-A mask blanks
  a whole stdout.

**The files of a run directory.** Tier B records the names of all files a run leaves in its output directory, also
of those whose content is not compared (the mesher's log). A file that is no longer written fails the comparison, and
so does a new one, unless the manifest lists its name under `allowed_new_files`: that is how a declared addition (a
new output file of every run) is admitted until the baselines are recorded again, when the list is emptied.

**The version.** Every `results.json` carries the package version (`/version`). It says which build wrote the file,
not what the build computed, so it is in no record: tier B blanks it like a masked value, tier C passes over it, and
both instead require it to be the version of the package that runs. A version bump therefore changes no baseline
([Releasing](release.md)), and a `results.json` that reports another version than its build still fails.

## The corpus of invalid documents

`tests/g0/corpus.json` holds documents that `axmp validate` refuses, each with the reason it is there. It holds **no
document whose only error is the key `physics` or one of the six reserved section keys** (`domains`, `boundaries`,
`reactions`, `couplings`, `study`, `outputs`): in 0.1.0 those produce "unknown field", and the model document replaces
that message deliberately with dedicated refusals that are asserted in that change's own tests. `tests/test_g0.py`
checks that no corpus document has such a top-level key.

## Running it

G0 needs a build (see [Building](building.md)); the commands use the in-tree Python package and the built `axmp`.

```bash
source scripts/env.sh
export PYTHONPATH=python AXMP_BIN=build/axmp AXMP_MESHER=build/axmp-mesher   # AXMP_EXE is read too; without either,
                                                                              # build-mpi/ and build/ are searched
python tests/g0/g0.py fingerprint            # the platform key and fingerprint
python tests/g0/g0.py check                  # tier A, then B and C, whichever apply here
python tests/g0/g0.py check --tiers A        # text only (seconds)
python tests/g0/g0.py check --only template_toroid,solve_3d_ring   # some tier-B/C entries (a name that is no entry is an error)
python tests/g0/g0.py pending                # what a recorded platform has no comparison for, and why
python -m pytest tests/test_g0.py            # tier A and the harness's rules; AXMP_SLOW=1 adds tiers B and C
```

`check` ends with `G0: passed` (exit status 0) or `G0: FAILED` (1). After a refused tier B the last line is
`G0: passed WITHOUT TIER B`, still with exit status 0 (above: what such a run leaves unchecked). When the tiers asked
for are ones that do not run on this host (`--tiers C` on the reference platform, `--tiers B` on a hosted platform,
`--tiers BC` on the gate's sequential build), it compared nothing: it says `G0: nothing compared here` and exits with
status 2, which is not a pass.

On the reference platform the run needs its platform name, because the platform key holds only the system, the
machine and the build kind:

```bash
export AXMP_G0_PLATFORM=lawrencium-x86_64-mpi      # on a node of the pinned type, in a batch job
python tests/g0/g0.py check --tiers AB --require-reference
```

Without the name the host presents as `linux-x86_64-mpi`. Two things override the key, and `check` prints which one
it used: the **fingerprint** (a host that has the reference's compared fields is compared as the reference platform),
and `--require-reference`, the host's **claim** to the role, which holds even when the fingerprint has moved — that
case is the failure the flag is for. `record` on the other hand refuses under the bare key, because it would
overwrite a hosted platform's baseline; recording needs the name.

`check` fails when anything it was asked to compare has no record: a design or a corpus document that the tier-A
baseline does not have (unless the platform is one that `tests/g0/pending.json` lists it as pending for), a tier-B
entry (a mesh entry included) that the platform's record does not have, an entry that the reference platform's record
does not have, and an `--only` list that names no entry or runs none. Failures print the first differing lines (tier
A), the differing figures and non-numeric leaves (tier B `results.json`) or the quantity, both values, the relative
difference and the tolerance (tier C).

**A machine that is neither the reference platform nor a hosted runner.** Such a machine can have the key of a
recorded platform: a Linux x86_64 cluster node with an MPI build has the key `linux-x86_64-mpi`, which is a hosted
platform's. What decides is the fingerprint. Under that key, `check` compares tier A with the committed baseline of
the key, does not run tier B (that platform is compared at tiers A and C), and runs tier C against the reference
platform's record with the tolerances measured on that key; `record` refuses to run (exit status 4), since it would
overwrite that platform's baseline. The better way is to give the machine a name of its own,
`AXMP_G0_PLATFORM=<name>`: `record` then writes `baseline/<name>/` (its tier A, its own tier-B record and masks, its
fingerprint) and `spread/<name>.json`, `g0.py tolerances` gives it tolerances of its own, and `check` compares it with
its own record in tier B and with the reference platform in tier C. That is how a second configuration, for example
the Eigen build, is held to its own bytes. A host whose key has no baseline compares tier A with
`--baseline-platform <key>`. Set `AXMP_G0_LAUNCH="mpirun -n 1"` where a launcher is needed to start a single-rank MPI
program.

Every merge runs tiers A and B on the reference platform, in a batch job on a node of the pinned type, and tier A of
the gate's sequential build in the gate's sequential job (through `tests/test_g0.py`, under the name
`lawrencium-x86_64-sequential`). `g0.yml` runs
`check` (tiers A and C) on the three hosted platforms in the public repository: on the push of a release tag (`v*`,
which is how a release is published, see [Releasing](release.md)) and on a pull request that changes code; in the
private development repository, where macOS minutes are billed at ten times the Linux rate, the macOS job runs only on
a manual dispatch. G0 is also an entry of the pre-merge subset (`tests/premerge.txt`).

### Pending entries

A new entry of the manifest or of the corpus has no record on a platform until it is recorded there.
`tests/g0/pending.json` lists, per recorded platform, its role, the entries the committed records give it no
comparison for, and **why**; `g0.py pending --write` generates it and `tests/test_g0.py` fails when it is not what the
committed records give, so it cannot go stale.

- **On the reference platform `check` fails while anything is pending there**, whatever it was asked to compare,
  because nothing else compares those entries byte for byte. In practice nothing is: the reference platform is
  recorded in the same commit that adds an entry. An entry that the reference record lists as **not reproducible**
  there is pending in the same sense and fails the same way (above): tier C does not run on the reference platform, so
  it has no comparison at all.
- **On a hosted platform a pending entry has its figures left uncompared, and is reported by name with the reason.**
  Those platforms are measured only by their own CI, so an entry added since their last record has no measurement
  there and therefore no tolerance for its figures; giving it one by hand, or comparing it at the floor, would be an
  invented number. The entry is still **run**, and its exit status still compared with the reference's, so a design
  that stopped solving there fails. `check` prints `PENDING` for each such entry and ends with how many are pending,
  so the output never claims more than it checked. What covers the figures meanwhile is the reference platform, at
  tiers A and B. They are recorded again by a `record` dispatch of `g0.yml` in the public repository (below), which
  empties the list.
- **The same rule holds for a single figure**, not only for a whole entry. A figure that the platform's measurement
  has no spread for — a figure added to a solve that the platform already has a record of — has no tolerance there, so
  tier C does not compare it and `check` counts it in the entry's line (`N not: no spread of them was measured here`).
  Comparing it at the floor instead, the strictest assertion the harness can make, would be an invented number. Of
  the figures committed today none is in this state: `tests/test_g0.py` checks that every figure of every entry a
  platform has a measurement of is either asserted or listed as unasserted there.
- A **mesh entry** is never pending on a hosted platform: tier C compares its exit status alone, which needs no
  measurement.
- On a machine with a name of its own, an entry that the reference platform has no record of is compared with the
  machine's own record alone, and `check` says so (`PENDING`); that is how a new entry is exercised before the
  reference record exists, and it is not a pass of the gate.

## What tier C asserts, and what it does not

Tier C compares another problem than tier B does: another compiler, another sparse LU, and where the mesher build
differs, another mesh. `tests/g0/tolerances.json` lists, per measured platform and per entry, the tolerance of every
figure and everything that is left out there, with the measurement behind it. Its `summary` gives the counts. A
platform is compared with the spread measured on it alone (its family is the platform key its figure record was
recorded under);
`any`, the worst case over all measured platforms, serves a platform that was not measured. Three classes of
figures:

- **Round-off** (`tolerances`). A figure whose spread from the reference platform's value is at most 1e-7 is
  asserted at `max(10 x the spread, 1e-10)`. The floor is the relative residual to which the engine's direct solves
  are gated (`direct_tol`); the ceiling of 1e-7 is the largest ceiling this project gives an exactness test (that of
  a Newton solve).
- **Over the ceiling** (`over_ceiling`: the tolerance, the spread and the platform that gave it). A figure that
  spreads more does so because the problem solved is not the same. The macOS mesher build makes other meshes than
  the Linux reference (for `example_long_solenoid_coax` 109000 elements against 108966, for `template_core` 68037
  against 68059), so anything that depends on the mesh beyond round-off, such as a force on a thin body, a pulse
  history in the HTS time stepping or a peak value, differs at the level of the discretisation. Such a figure is
  asserted at ten times its measured spread d, as long as the platform's own value, halved, would still be outside
  that tolerance: halved, it is off the reference by at least 0.5 - d/2, so the condition is 10 d < 0.5 - d/2, a
  spread below 0.5/10.5 = 0.048. This is a **coarse check**: a change by a factor of two fails for every figure of
  the class (`tests/test_g0.py` shows it for each of them on each platform's record), and a change below the size of
  the spread passes. On macOS the
  top-line coupling figures of `example_hts_shield` are in this class (`/coupling/g_factor`,
  `/coupling/Psi_SI_H_T_m2`, `/coupling/F_SI_T4_H2_m8`, `/coupling/W_mag_J` and the two in natural units: spreads of
  6e-7 to 2.4e-6, another mesh and then the critical-state time stepping), and so are `/fields/B_max_T` of
  `template_core` (4.0e-4) and of `template_solenoid` (2.2e-5).
- **Unasserted** (`unasserted`: the spread and the platform). A figure that spreads by more than that cannot be
  given a tolerance that still fails a factor of two, and tier B on the reference platform is what holds it. What is
  on this list, by measurement:
    - Figures that are themselves round-off, on every platform: a residual or a "relative difference" check that is
      about 1e-12 on one platform and 3e-12 on another has a relative spread of order one, and so has a figure that
      is zero up to rounding (the net current of a superconducting body that is constrained to carry none, 5e-6 A). Such a
      quantity is judged by the verdict of the check that carries it (`valid`, `holds`, `pass`), which tier C compares
      exactly on every platform, not by a tolerance on its value.
    - The size of the last Newton updates of the HTS time stepping (`/hts/steps/*/newton_update`,
      `/hts/newton/max_update`: about 1e-6, differing by 6 % to 80 % between platforms). They measure how far
      below its tolerance an iteration stopped, not a result; the `converged` flags are compared exactly.
    - On macOS only, quantities decided by the mesh: net axial forces that are the small remainder of large
      contributions (`Fz_N` of the shield and the solenoid in `example_hts_shield`, 9 % to 16 %; of the cavity in
      `template_core`, 47 %; of the winding and the outer conductor in `template_solenoid`, 6 % to 14 %), the two
      terminal areas of the port capacitance of `example_hts_shield` and `template_solenoid`
      (`/pickup/port_capacitance/terminal_area_m2/0` and `/1`), and `/fields/B_max_location/z_m` of the
      mirror-symmetric `template_core` (the peak sits at -0.995 m on one mesh and at +0.995 m on the other). The
      terminal areas are a case of their own: the areas agree with the reference platform's to round-off (a few
      1e-16), and what differs is the **order** in which the two terminals are listed, which is exchanged there. Tier C
      compares a list element by element, so it sees one terminal's area against the other's (46 % to 123 %). In the
      other two solves that have the list (`example_long_solenoid_coax`, `template_core`) the order is the
      reference's on macOS and the areas are asserted. `tolerances.json` has the complete list. On macOS these quantities are
      not compared at all: no platform but the reference has a byte record, and there they are what the mesh makes
      them. What holds them is the reference platform's tier B, and the physics checks of the test suite, whose
      verdicts tier C compares exactly everywhere.

The counts, of 4759 figures that are not mesh sizes, in the seven solves every platform has a measurement of, each
against the reference platform's record: the hosted Linux MPI platform has 4614 in the round-off class, 76 over the
ceiling and 69 unasserted; Linux sequential 4428, 95 and 236; macOS 3107, 1271 and 381. The two sequential platforms
spread more than the MPI one because their mesher is a packaged gmsh and their build is sequential; macOS more again
because its mesher makes other meshes.

**Why the over-ceiling class exists.** A figure over the ceiling was at first not asserted at all, which left the
macOS job blind to the headline figures of one example. The class gives every such figure a tolerance against the one
reference record: it needs nothing but the measurements already committed, it survives a platform that moves (a new
runner image or compiler changes the last digits, not the figure at the level of its spread), and it keeps one source
of truth. What it cannot do is see a change smaller than the spread.

The other remedy — a byte record per platform, which sees every changed byte on that platform's own mesh — holds only
while the platform's fingerprint is the recorded one, and a hosted runner takes its compiler and system libraries from
the image, which moves. That is why tier B is pinned to one node type instead, where the fingerprint is the project's
to keep, and why on every other platform the coarse check above is what remains. Neither replaces the reference
platform's own byte comparison, which is the only one on a pinned mesher build and a pinned processor.

**What is not a number** (`unasserted_discrete`: the reference's value and each platform's;
`unasserted_layout`: the pointers). Everything else that is not a number is compared exactly. Measured to differ:

- `/mesh/info/mesher/gmsh_version` on a platform whose mesher links another build of the same gmsh release: the
  reference platform links the gmsh SDK of the shared third-party stack, which calls itself `4.15.2`, while the
  hosted MPI platform builds the SDK with `scripts/build_deps.sh`, which calls itself `4.15.2-nox`. It is build
  identity (the fingerprint's `mesher` field), not a result.
- On macOS, in `template_core`: `/fields/B_max_location/region` (`coil_lower` on the reference, `coil_upper` there)
  and the lengths of the seven per-element lists under `/forces/distributions/lower/` (179 on the reference, 200
  there). The design is mirror-symmetric (the peak sits at z = -0.995 m on one mesh and z = +0.995 m on the other),
  so which of the two coils holds the peak is decided by the mesh, and the list lengths are element counts.

No boolean is on these lists on any platform: every verdict of a physics check agrees with the reference's
everywhere, and `tests/test_g0.py` keeps it so.

Arrays of more than 64 numbers (the per-element distributions) are compared in tier B only; tier C asserts their
lengths through the layout.

## Baselines change only through a separate commit

A baseline is a record of behaviour that users can observe; it never changes as a side effect of another change.

1. If a change makes G0 fail, the change is wrong unless the behaviour change is intended and declared in the pull
   request that makes it. Fix the change, not the baseline.
2. For an intended change, a **separate commit** re-records the baseline, with a release note in `CHANGELOG.md` and a
   message that says what behaviour changed and why. It contains the regenerated files and nothing else. A version
   bump is not such a change (the version leaf is in no record).
3. Never edit a file under `tests/g0/baseline/` or `tests/g0/spread/`, nor `tests/g0/tolerances.json` or
   `tests/g0/pending.json`, by hand: `g0.py record` writes the first two, `g0.py tolerances` and `g0.py pending
   --write` the others.
4. A tolerance is never loosened to make a check pass; if a figure moves, find out why first. `g0.py tolerances`
   enforces the rule as `record` does for the masks: a derivation that asserts less than the committed file (a
   tolerance that grew, a figure that left the round-off class for the one over the ceiling, a figure, a
   non-numeric leaf or a layout pointer that is no longer asserted, a family that is gone) stops with exit status 3
   and lists the places, unless `--allow-loosening` is given for a reviewed change that the commit argues. A
   developer host's spread loosens nothing that a recorded platform is compared with, because every platform has its
   own family. `tests/test_g0.py` checks that the committed file is exactly the derivation from the committed records.
5. Adding a design to the manifest or the corpus adds to the baseline (a re-recording); it never alters an existing
   entry. Until the re-recording is committed the new entry is pending (above).

### Recording the reference platform

The reference platform is recorded where it is compared: in a batch job on a node of the pinned type, from a built
checkout of the branch.

```bash
export AXMP_G0_PLATFORM=lawrencium-x86_64-mpi
export PYTHONPATH=python AXMP_BIN=build-mpi/axmp AXMP_MESHER=build-mpi/axmp-mesher
python tests/g0/g0.py record                      # the fingerprint as committed, no new mask
python tests/g0/g0.py record --allow-new-masks    # new manifest entries: their timing masks are new
python tests/g0/g0.py record --repin              # the platform moved (compiler, system, mesher), or the harness
                                                  # writes other fingerprint fields: a separate, argued commit
python tests/g0/g0.py tolerances   # exit status 3 lists what would be asserted less strictly: read it before
                                   # deciding on --allow-loosening
python tests/g0/g0.py pending --write
python -m pytest tests/test_g0.py
git add tests/g0 && git commit     # the baseline commit: these files and nothing else
```

It writes `baseline/lawrencium-x86_64-mpi/` (its tier A, its tier-B record, its figures, its masks, its fingerprint).
Then the record is **checked again on other nodes of the pinned type** (`check --tiers AB --require-reference`), which
is what separates a run-to-run difference from a machine-to-machine one.

`record` refuses (exit status 4) on a host whose fingerprint is not the one committed for its platform key; `--repin`
is the argued re-recording of a platform that moved. It never covers another processor model (the pin itself) and
never a reference fingerprint without a compiler.

### Recording the gate's sequential build

The text record of `lawrencium-x86_64-sequential` is made on the cluster too, in a batch job, from a checkout built
the way the gate's sequential job builds it (the site compiler, the sequential stack of
`scripts/build_deps_wheel.sh`, gmsh from PyPI). It is a second checkout, because the in-place module of a build
goes to `python/axionmultiphysics/` and a checkout holds one.

```bash
export AXMP_G0_PLATFORM=lawrencium-x86_64-sequential
export PYTHONPATH=python AXMP_BIN=build-seq/axmp AXMP_MESHER=build-seq/axmp-mesher
python tests/g0/g0.py record       # tier A only: runs no solve, writes tierA.json, masks.json and fingerprint.json
python -m pytest tests/test_g0.py
```

Its three files go into the same baseline commit as the reference platform's. Whenever the reference's tier A is
recorded again (a new design or corpus document, a declared change of a text), this one is too: the gate's
sequential job fails until it is, and nothing is ever pending there. `record` does not refuse for the processor
model on this platform (the job is not pinned to a node type, and a text does not depend on it); for another
compiler, system or mesher it wants `--repin`, as everywhere.

### After a declared change of a text: the hosted records

Tier A is one record per platform, and the baseline commit of a declared text change re-records the two that the
cluster can make: the reference platform's and the gate's sequential build's. That is all the development gate
compares, so it passes. **The tier-A records of the three hosted platforms are then stale**: they hold the old text,
and `check` fails tier A on each of them. Nothing in the development repository can make them again. They are
recorded by a `record` dispatch of `g0.yml` in the **public** repository (next section), and **that dispatch and its
baseline commit come before the release tag**, because pushing the tag runs `g0.yml` on the three hosted jobs
([Releasing](release.md)). Until then a build on a developer machine that runs under a bare hosted
key (no `AXMP_G0_PLATFORM`) fails tier A for the same reason.

### Recording a hosted platform

The three hosted platforms are recorded by their own CI, in the public repository, because that is the only place
those images exist. One dispatch records all three:

```bash
gh workflow run g0.yml --ref <branch> -f record=true            # every fingerprint as committed (the processor
                                                                # model aside), no new mask
gh workflow run g0.yml --ref <branch> -f record=true -f allow_new_masks=true   # new manifest entries: their timing masks are new
gh workflow run g0.yml --ref <branch> -f record=true -f repin=true             # a runner image that moved (system,
                                                                               # compiler, mesher): an argued commit
```
**The processor model is no ground for `record` to refuse on a hosted platform**, nor on the gate's sequential
build. `cpu` is a compared fingerprint field because it pins the reference platform's bytes. A hosted job is given
whichever processor model the runner fleet has that day, and no record of bytes is compared there (tiers A and C
only), so the model pins nothing. If it were a ground for refusal, the plain form would succeed or fail by the draw
of the runner, also directly after a `repin` record, and `repin=true` would become the form always passed, which is
what it must not be: it stands for an argued re-recording of a platform that moved. The model is still written into
the fingerprint. So the plain form works whenever the other compared fields are the committed ones (the committed
fingerprints of the three were written before the model was a field at all, which is no obstacle either); when
another field moved, `record` exits with status 4 and names it, and the record is a `repin=true` one. On the
reference platform, and on a host with a name of its own, whose own bytes are compared, the model still refuses.

Add `allow_new_masks=true` for the manifest entries added since a platform's last record: a plain `record=true` stops
with exit status 3 when a recorded entry has no timing mask yet. Use it whenever `tests/g0/pending.json` lists tier-B
entries for a hosted platform, as the release steps do.

Each job uploads one artifact, `g0-<platform>`, rooted at `tests/g0/`, with that platform's files and no other's
(`baseline/<platform>/` and `spread/<platform>.json`), so the order in which they are unpacked cannot matter. Then,
in a checkout of the branch:

```bash
gh run download <run id> -D /tmp/g0-artifacts
for d in /tmp/g0-artifacts/g0-*; do cp -r "$d"/. tests/g0/; done
# a platform that once was the reference also has baseline/<platform>/figures.json; its measurement is now the spread
# file, so the superseded one goes (`tolerances` refuses while both are there)
git rm -q --ignore-unmatch tests/g0/baseline/linux-x86_64-mpi/figures.json
python tests/g0/g0.py tolerances       # the spread of each platform against the reference platform's record
python tests/g0/g0.py pending --write  # the pending lists of the recorded platforms shrink
python -m pytest tests/test_g0.py      # on a host with a build, under its own AXMP_G0_PLATFORM name
git add tests/g0 && git commit         # the baseline commit: these files and nothing else
```

A hosted platform's tier-B record is written by `record` but compared by nothing: it is the evidence of the
reproducibility measurement there, and it is what a promotion of that platform would start from.

The baseline commit message names where every platform was recorded (the node for the reference platform, the
workflow run for a hosted one) and the commit it ran on, and says what `masks.json` gained (with `allow_new_masks`)
and what moved (with `repin`). Read the new masks before committing: every tier-B mask must be a timing, and an entry
listed by name is an entry without a record on that platform, with the reason beside it. Every recorded fingerprint
carries the recording commit (`informational.build_info.git_sha`).

`gh workflow run` starts only a workflow whose file is on the default branch. Until `g0.yml` is there, the recording
commit cannot be a commit of the branch: it is then a throwaway commit that differs from a named commit of the
branch **only in files under `.github/workflows/`** (the G0 workflow under the file name of a workflow that the
default branch has), the baseline commit message states that difference, and
`git diff --stat <branch commit> <recording commit>` shows it.

## Testing the gate

A gate that cannot fail is worthless. When the gate or a tier changes, show once, out of tree (a throwaway patch or a
wrapper around `axmp` given as `AXMP_BIN`, not committed), that it fails for an EM-visible change: a changed
`validate` message, a changed exit status, a changed number and a re-spelled number in a tier-B `results.json`, a
file that is no longer written, and a changed mesher input.
